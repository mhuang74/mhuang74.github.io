## Problem

I built [Stream of Worship](https://www.streamofworship.com/about) to help small group leaders play Mandarin worship songs without interruptions. Playing lyrics videos from YouTube means switching between songs and depending on the network to hold up. The pauses break the flow, and a dropped connection can leave everyone waiting.

There aren't many lyrics-video options for Mandarin worship. I wanted a leader to pick songs, render a continuous set with synchronized lyrics, and cast it to the TV. The output is one audio file and a lyrics video with chapter markers, ready for offline playback. No manual audio editing needed.

## Constraints

Three things shaped the project:

1. **Playback has to work offline.** The network problems were part of the reason for building this. Downloading the set before worship had to work from the start.
2. **Accurate LRC files are hard to find.** The lyrics have to match what is actually sung in the recording, including every verse and chorus repetition, with an accurate timecode for each line. Getting both the words and timing right took a lot of work.
3. **ASR still needs human review.** Automatic speech recognition (ASR) models made plenty of mistakes on the Chinese songs I worked with, even Alibaba's Qwen3 ASR. Creating an LRC file from scratch wasn't as simple as feeding the audio to Whisper or Qwen3. I needed to automate as much as I could and build a human-in-the-loop process to validate and correct the LRC files.

## Decisions

**Keep the components separate**

The monorepo has 9 components. I kept ML dependencies in the Dockerized Analysis Service, and routed the admin CLI and Android client through APIs rather than letting them access Postgres, R2, or SQS directly. These boundaries are conventions documented in AGENTS.md. For a solo project I expect to maintain for years, I wanted the interfaces to be explicit.

**Look at where songs meet**

Whole-song key and tempo averages can produce jarring transitions. I use the key and BPM at the end of one song and the beginning of the next to judge how well they fit together.

The songset constructor uses beam search to find sets across five worship phases （讚美 → 感恩 → 敬拜 → 奉獻 → 差遣）. It scores theme, tempo flow, harmonic mix, and diversity. Hard constraints can be relaxed through configuration when the search needs more room.

**Give tempo estimation some context**

Off-the-shelf tempo estimators can get confused by worship arrangements and return half or double the tempo. I added BPM priors for worship music, plus a lognormal prior derived from lyrics characters per second, to help resolve that ambiguity.

**The lyrics pipeline needs fallbacks**

The pipeline chains YouTube transcripts → cloud ASR → local Whisper → LLM alignment → a forced aligner. A circuit breaker handles repeated YouTube transcript failures. When an API hits its free-tier quota, jobs wait for the quota to reset. Separate semaphores for each job class keep catalog backfills from taking all the capacity needed by live requests.

**Render in Lambda**

An AWS Lambda container takes render jobs from SQS and produces crossfaded multi-song MP3s and lyrics MP4s of around 29,000 frames. The browser receives progress through server-sent events (SSE). This keeps the long-running render work out of Vercel functions.

**Download the set before worship**

The web app caches rendered files in a service worker, with byte-range serving for large videos. Share links point to frozen copies scoped to a token, so later edits don't change the set someone else received. I recorded that decision in ADR 0009.

I think the ranking is the useful part. Proposal 1 scores higher on tempo flow (0.642 vs 0.526) and harmonic mix (0.780 vs 0.620), but proposals 3 and 4 come within 0.15 of its composite score with entirely different openings. In proposals 2 and 5, the constructor accepts a 4-second crossfade with a +1 semitone key shift into the closing song. These are tradeoffs a leader can inspect when choosing a set.

## Outcome

The system is built to handle a catalog of 400+ songs, with 191,406 scored pairwise transitions in the eval harness. The work includes ~500 versioned spec documents with v1–v5 iteration chains, 11 ADRs, and 150+ Vitest files for the web app alone. CI runs against a real Postgres instance with pgvector.
